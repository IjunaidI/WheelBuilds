# WB-100 · Availability signals in discovery — design

> G12 Wave A (discovery & merchandising), chunk 3 of 3. Finding **WB-100** ([spec §WB-100](../../future/specs/2026-07-13-ux-completeness-fixes-design.md)).
> Scouted against current `main` (`8035b6c`) 2026-07-16 — evidence inline. **Backend + storefront. The only Wave-A chunk needing a Meili re-index to go live.** Depends on WB-089 (done — the reconcile machinery this reuses).

## Problem
Neither Meili doc type carries a stock field ([build-search-document.ts](../../../backend/src/modules/vendor-sync/search/build-search-document.ts)), so a sold-out product is indistinguishable from a buyable one on the grid until the shopper opens its PDP — clicks invested in something they can't buy. The transformer's input is deliberately narrow: `MEILI_PRODUCT_FIELDS` ([meili-index-settings.ts:9-14](../../../backend/src/modules/vendor-sync/search/meili-index-settings.ts#L9-L14)) is `id/title/description/handle/thumbnail/created_at/status/metadata/variants.sku/variants.metadata/variants.prices.*` — **no inventory path**, so the transformer literally cannot see stock today. The only variant filter it applies is the `discontinued` metadata flag ([build-search-document.ts:55-57](../../../backend/src/modules/vendor-sync/search/build-search-document.ts#L55)) — a permanent "delisted" mark, not "sold out right now."

## Decisions (defaults + approved)
- **Freshness: ~3h (approved).** The 3-hourly stock refresh (`runStockOnly`, cron `0 */3 * * *`) drives the grid's `in_stock` freshness by re-indexing after it applies stock. A just-sold-out wheel drops its badge within ~3h. The existing daily `meilisearch.sync` reconcile ([meilisearch-reconcile-tick.ts](../../../backend/src/jobs/meilisearch-reconcile-tick.ts)) stays as belt-and-braces.
- **Show + badge, toggle default OFF (approved).** Out-of-stock products stay in the grid with an OUT-OF-STOCK badge; an "In stock only" toggle (default off) adds an `in_stock = true` filter. Keeps the catalog looking full and lets a shopper see a wheel exists + open its PDP for the WB-098 lead-time/ETA signal.
- **Product-level `in_stock` = "≥1 buyable variant."** A wheel has many variants (sizes/offsets/finishes); the product is "in stock" if **any non-discontinued variant has real available stock (> 0)** — matching the PDP's best-of-siblings availability. Only when *every* variant is out does the badge show.
- **Source the stock at index time via field-widening (primary), metadata-mirror (verified fallback).** Primary: widen the plugin's indexed fields to a remote-query inventory path so the transformer reads real available stock and computes `in_stock` fresh on every index — single source of truth, no drift, no second write path. `apply.ts` already proves `variants.inventory_items.*` is reachable from a variant graph query, so the path shape is plausible. **The plan's first task VERIFIES the exact Medusa 2.13.6 remote-query path resolves stocked/reserved from the plugin's `fields` config**; if it does not, fall back to mirroring a boolean onto `variant.metadata.in_stock` at stock-apply time (reuses the already-indexed `variants.metadata`, so zero further widening). The storefront work is identical either way.

## Design

### Backend (needs a re-index to activate)
1. **`in_stock` on both doc types.** `buildWheelDocument` + `buildTireDocument` compute `in_stock: boolean = OR over non-discontinued variants of (availableQty > 0)`. Available = stocked − reserved (or the metadata-flag fallback). The `null`-transformer stub ([medusa-config.js:299-314](../../../backend/medusa-config.js#L299)) gets a safe `in_stock: false` default so a displayed/filtered attribute never references a missing field.
2. **Index settings** ([medusa-config.js:282-296](../../../backend/medusa-config.js#L282)): add `in_stock` to `filterableAttributes` (and `displayedAttributes`). Settings take effect on the next backend boot; document *content* (the actual `in_stock` values) backfills on the next full reconcile — so a re-index is the deploy step.
3. **Freshness wiring (~3h).** After `applyStockLevels` completes in `runStockOnly` ([service.ts:493-572](../../../backend/src/modules/vendor-sync/service.ts#L493)), emit `emitMeiliReconcile(container)` ([meili-reconcile.ts:14-19](../../../backend/src/modules/vendor-sync/meili-reconcile.ts#L14)) so the transformer re-runs over published products and picks up the fresh stock. **Plan checks first** whether the field-widening/metadata write already triggers a *targeted* per-product re-index via the plugin's event subscription — if it does, the explicit full reconcile is redundant and we prefer the targeted path (fresher + cheaper than a full 8×/day reconcile); if not, the explicit `emitMeiliReconcile` is the mechanism (the approved full re-index). Cost note: the targeted path re-indexes only the changed parts (`applyStockLevels` already computes that delta), whereas the full-reconcile path re-indexes every published product each run (~2,700 docs, 8×/day) — acceptable at this catalog size per the approved ~3h decision, and the reason the plan prefers the targeted path if the plugin's event subscription supports it.
4. **Backend tests** (`test:sync`): the transformer's `in_stock` OR-across-variants (some-in-stock → true; all-out → false; all-discontinued → product dropped as today); the stub default; the reconcile-after-stock wiring (a unit over the `runStockOnly` call order, not a live Meili hit).

### Storefront (rebuild)
5. **Types + data layer.** `DiscoveryProduct` gains `inStock: boolean` ([discovery/data/types.ts](../../../storefront/src/modules/discovery/data/types.ts), mirroring the existing `isNew` boolean); `DiscoveryFilters` gains `inStockOnly?: boolean` (an optional scalar, same shape family as `priceMinCents` — NOT an array facet). `hitToProduct` reads `hit.in_stock`; `buildFilters` pushes `in_stock = true` when `inStockOnly` ([get-products.ts:54-75](../../../storefront/src/modules/discovery/data/get-products.ts#L54-L75)). Same for the tire twin (`TireDiscoveryProduct`/`TireDiscoveryFilters`/`hitToTireProduct`).
6. **OUT-OF-STOCK badge** on both cards ([discovery/.../product-card.tsx](../../../storefront/src/modules/discovery/components/grid/product-card.tsx), tire card): an absolutely-positioned chip in the image wrapper, placed to not collide with the `NEW` chip (`top-left`) or the fit badge — e.g. `top-right` — gated on `!product.inStock`. Uses the WB-096 contrast tokens.
7. **"In stock only" toggle** in both rails' `filter-sections.tsx`: a single `<Checkbox>`/switch bound to `filters.inStockOnly` via `replaceScalars({ inStockOnly: true | undefined })` (the same commit path price uses — NOT a `ChecklistSection`, which expects a multi-value `facetMap`). Default off. It rides the disjunctive-facet machinery cleanly: a boolean filter narrows the hits + every facet query, so counts stay honest.
8. **`useDiscoveryQuery`** gains a `setInStockOnly` (or reuses `replaceScalars`) + reflects the param in active-chips ("In stock only" as a removable chip). Same for the tire query hook.

## Verify
Backend: `npx jest src/modules/vendor-sync` (`test:sync`) green incl. the new `in_stock` transformer cases; `cd backend && npx medusa build` exit 0. Storefront: `npx vitest run` incl. the `inStockOnly` filter clause + `hitToProduct` in-stock mapping; `npx tsc --noEmit` at/below the **2-error baseline**; `npx next build`; `npx next lint`. **Live smoke against a re-indexed dev index**: a zero-stock product shows the OUT-OF-STOCK badge on `/store` and `/tires`; the "In stock only" toggle excludes it and updates the count; toggling it writes/removes the URL param + the active chip; an in-stock product is unbadged. Confirm the `in_stock` field is present + filterable in the Meili index after a reconcile.

## Deploy
**Backend deploy + a Meili re-index** (the `meilisearch.sync` reconcile, or a boot-time sync) so every doc carries `in_stock` and the attribute is filterable — the settings apply on boot but the field values backfill on the reconcile. Then a storefront rebuild. No DB migration (field-widening reads existing inventory; the metadata-mirror fallback writes only variant metadata, no schema change).

## Out of scope
Low-stock ("only N left") signals on the grid (the PDP already shows exact counts — WB-098; the grid badge is binary). Per-variant/per-size availability on the card (the card is product-level). A stock sort. Backorder/pre-order flows. Real-time (sub-3h) stock — the ~3h cadence is the approved trade.
